## 3 - JavaScript 린트

검사 세트: ESLint recommended + `no-var`, `prefer-const`, `eqeqeq` 등 프로젝트 권장 규칙

로드되는 스크립트 8개 중 `remote_4_gsap.min.js`, `remote_5_ScrollTrigger.min.js`, `remote_6_ScrollSmoother.min.js`, `remote_7_ScrollToPlugin.min.js`, `remote_8_swiper-bundle.min.js`, `remote_2_browser_4.js`(Tailwind CDN 런타임)는 전부 외부 CDN에서 그대로 받아 쓰는 압축 라이브러리다. 여기서 나온 오류·경고(총 900건 이상)는 직접 만든 코드가 아니므로 표에서 뺀다.

자체 코드는 두 파일이다: 문서 맨 아래 인라인 `<script>`(`inline_1.js`)와 `common/components.js`(`remote_3_components.js`).

직접 작성 코드 오류는 `inline_1.js` 17건과 `remote_3_components.js` 76건으로 총 93건이다. CDN 전역 및 브라우저 API 관련 `no-undef`는 린트 환경 설정에 따른 오탐이며, 실제 동작 문제 후보는 모바일 메뉴 관련 미선언 변수 5건이다.

데스크톱은 회선·기기 성능이 좋다는 가정 때문에 모바일보다 점수가 높지만, LCP는 여전히 25% 비중에서 0.08점(거의 최저)로 발목을 잡는다.

원인은 두 기준에 공통이다. 페이지 총 전송량이 10,660 KiB로 동일하며, 이미지 최적화로 모바일 8,868 KiB / 데스크톱 7,284 KiB, 캐시 정책으로 9,620 KiB를 절약할 수 있다는 진단이 나왔다. 렌더링 차단 리소스(주로 head에 동기 로드된 Tailwind CDN·GSAP·Swiper 스크립트)는 모바일에서 8,150 ms, 데스크톱에서도 240 ms 절약 여지가 있다는 진단이다. `width`/`height`가 없는 이미지도 있어 레이아웃 이동(CLS)에 일부 기여한다.

자동 검사로는 아래 세 가지가 확인되지 않습니다. 직접 해 보고 판단합니다.

1. 키보드 `Tab` 키만으로 화면 전체를 쓸 수 있는가 — 특히 위 3번 항목에서 발견한, `mobileMenu` 관련 코드가 깨지는 경우 모바일 메뉴 키보드 접근이 실제로 되는지
2. 포커스가 한 곳에 갇히지 않는가
3. 눈에 보이는 순서와 코드 순서가 맞는가

## 6 - 검색 최적화와 권장 사항

두 항목 모두 100점으로 자동 검사에서 걸린 항목 없음.

## 7 - 먼저 할 일

1. 이미지 용량(8,868KiB 절감 가능)과 캐시 정책(9,620KiB 절감 가능)을 손보고 LCP 이미지를 HTML에서 즉시 발견하도록 `preload` 또는 `fetchpriority="high"`를 검토한다. 모바일 LCP 36.9초와 성능 51점 개선에 가장 직접적이다.
2. 인라인 스크립트의 `mobileMenu`/`menuBtn`/`menuIconOpen`/`menuIconClose` 미선언 버그를 고친다. `document.getElementById`로 실제 DOM 요소를 가져오면 앵커 클릭 시 발생할 수 있는 `ReferenceError`를 막을 수 있다.
3. HTML 228번째 줄의 `div[aria-label]`에 적절한 `role`을 추가해 문법 오류를 없앤다.

## 검사 도구와 한계

이 보고서는 W3C Nu HTML Checker, W3C CSS Validator, ESLint(recommended), Lighthouse 결과를 옮긴 것입니다. 문법 검사는 코드가 규칙에 맞는지만 보므로, 문법이 맞아도 화면이 의도와 다르게 보일 수 있습니다. 린트는 자주 나오는 실수 위주로 잡으며, 팀 관습이나 프로젝트별 규칙까지는 판단하지 않습니다. 성능 점수는 잴 때마다 몇 점씩 달라지므로 한 번의 값으로 판단하지 않습니다. 접근성 점수(96점)는 자동으로 잡히는 항목만 반영하며, 키보드 이동이나 포커스 순서는 사람이 직접 확인해야 합니다.
