### 경고 1건

`index.html:477`의 영웅 영역 제목이 `h1`이다. 현재 페이지의 대표 제목으로 사용되므로 요소 자체는 적절하지만, W3C 검사기는 섹션 내부의 `h1`을 최상위 제목으로 해석할 수 있다는 일반 경고를 냈다. 문서 전체에 대표 `h1`이 하나뿐인지 유지하고, 섹션 제목은 `h2` 이하로 구성하면 된다.

## 2. CSS 문법

- 오류 31건 중 30건은 `swiper@12/swiper-bundle.min.css`에서 발생했다. 외부 라이브러리의 최신 CSS 문법을 검사기가 완전히 해석하지 못한 결과이므로 프로젝트 코드에서 직접 수정할 대상이 아니다.
- 프로젝트 코드의 실제 지적은 `assets/css/style.css:434` 한 건이다.

```css
width: calc(100% + var(--spacing-value-card-copy-overflow-lg) + var(--spacing-value-card-copy-overflow-lg));
```

브라우저에서는 유효하게 계산될 수 있지만 W3C 검사기가 `100% + var(...)`의 형식을 판정하지 못했다. 화면 동작을 확인한 뒤, 동일한 간격을 양쪽 여백·부모 너비·별도 계산 토큰으로 표현하면 검사기 호환성을 높일 수 있다. 단순히 식을 삭제하면 카드 문구 배치가 달라질 수 있으므로 시각 확인 없이 변경하면 안 된다.

경고 154건도 대다수가 외부 Swiper CSS의 공급사 접두사와 최신 문법에 관한 것이다.

LCP 요소는 `section#section1`의 `img.hero__bg`, 즉 `assets/images/hero.webp`다. 초기 HTML에서 바로 발견되고 지연 로딩도 하지 않지만 `fetchpriority="high"`가 없다. 해당 이미지에 높은 우선순위를 지정하고, 모바일·데스크톱에 맞는 `srcset`/`sizes`를 제공하는 것이 우선이다.

렌더링 차단 자원은 Tailwind Browser CDN, Swiper CSS, `assets/css/style.css`, `common/components.css`, `assets/css/fonts.css`다. 기준 측정에서는 약 1.07초의 절감 가능성이 잡혔다. 가장 근본적인 해결은 Tailwind 브라우저 런타임을 배포용 사전 빌드 CSS로 전환하는 것이다.

캐시 수명 개선 예상치는 약 4.2MiB이지만 GitHub Pages의 캐시 헤더는 프로젝트 HTML에서 직접 제어하기 어렵다. 우선 파일 자체 크기를 줄이고, 내용 변경 시 파일명 해시를 사용하는 방식이 현실적이다.

자동 검사 점수는 모바일·데스크톱 모두 96점이다. 주요 실패 항목은 색상 대비다.

자동화 검사로는 키보드 탭 순서, 포커스 갇힘, 동적으로 표시되는 콘텐츠의 초점 이동, 시각 순서와 DOM 순서의 일치 여부를 확정할 수 없다. 이 네 항목은 실제 브라우저 수동 검사가 필요하다.

## 7. 먼저 할 일

1. `social-instagram-1.png`, `social-instagram-2.png`를 모바일 표시 크기에 맞춘 WebP/AVIF로 교체한다. 모바일 전송량과 성능 점수에 가장 큰 영향을 준다.
2. `hero.webp`에 `fetchpriority="high"`를 추가하고 반응형 이미지 후보를 제공한다. 모바일 LCP 6.7초 개선의 직접 대상이다.
3. 대비 3.18:1인 연두색 텍스트·배지에 본문용 진한 녹색 토큰을 적용한다. 접근성 96점의 실패 원인을 해소할 수 있다.

## 검사 도구의 한계

이 보고서는 자동화 검사 결과다. Tailwind v4의 `@theme`, `@utility`와 외부 라이브러리의 최신·압축 코드는 W3C/ESLint에서 오탐이 발생할 수 있다. Lighthouse 점수는 네트워크와 실행 환경에 따라 달라지므로 한 번의 점수로 품질을 단정하면 안 된다. 자동 접근성 검사도 키보드 사용성과 실제 읽기 흐름 전체를 보장하지 않는다.
