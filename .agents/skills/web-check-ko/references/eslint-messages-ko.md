# ESLint 규칙 한국어 대응표

ESLint의 `eslint:recommended` 세트에 있는 규칙과, 최신 표준(ES2025+)에서 자주 걸리는 규칙을 한국어로 옮긴 표다. 검사 결과에 나온 규칙 이름(예: `no-unused-vars`)을 이 표에서 찾아, 학습자에게 무엇이·왜·어떻게를 한 문장으로 전달한다.

메시지는 원문을 괄호로 함께 남긴다. 학습자가 규칙 이름으로 검색해 공식 문서를 찾아볼 수 있어야 한다.

## 판정 강도

- **error(오류)**: 문법이 깨졌거나 실행 중 버그로 이어질 가능성이 큰 것. 반드시 고친다.
- **warning(경고)**: 실행은 되지만 최신 표준·팀 관습과 맞지 않는 것. 고쳐두면 좋은 것.

이 스킬의 기본 세트는 오류만 켜두므로, 결과에 `severity: 2`는 오류, `severity: 1`은 경고로 옮긴다.

---

## 1. 문법·파싱 오류

### Parsing error

- **뜻**: 코드가 JavaScript 문법에 맞지 않아 파서가 읽지 못한 상태.
- **왜 문제**: 브라우저가 이 파일 전체를 실행하지 못한다.
- **고치는 법**: 오류가 가리키는 줄의 앞뒤 괄호·따옴표·세미콜론을 확인한다. 대개 `(`가 하나 열리고 안 닫혔거나, 문자열이 줄바꿈으로 끊긴 경우다.

---

## 2. 변수·스코프

### `no-unused-vars` — 안 쓰는 변수

- **뜻**: 선언은 했는데 어디에서도 읽지 않는 변수.
- **왜 문제**: 죽은 코드가 남아 있으면 나중에 읽는 사람이 헷갈린다.
- **고치는 법**: 변수를 지운다. 이벤트 콜백의 매개변수처럼 시그니처상 남겨야 하면 이름을 `_`로 시작한다.

```js
// 나쁨
const total = 10;

// 좋음
const total = 10;
console.log(total);
```

### `no-undef` — 선언 없이 사용

- **뜻**: `let`·`const`·`function` 어디에서도 선언되지 않은 이름을 그대로 씀.
- **왜 문제**: 실행 중 `ReferenceError`가 난다.
- **고치는 법**: `import` 문을 빠뜨렸는지 먼저 확인한다. 브라우저 전역(`window`, `document`)은 환경 설정에서 켠다.

### `no-var` — `var` 사용 금지

- **뜻**: `var`로 변수를 선언한 코드.
- **왜 문제**: `var`는 함수 스코프이고 호이스팅되어 예기치 못한 값 덮어쓰기를 일으킨다. ES6 이후 `let`·`const`가 표준이다.
- **고치는 법**: 다시 대입할 값이면 `let`, 한 번만 대입할 값이면 `const`로 바꾼다.

```js
// 나쁨
var count = 0;

// 좋음
let count = 0;
```

### `prefer-const` — 재할당 없는 변수는 `const`로

- **뜻**: `let`으로 선언했지만 이후 한 번도 다시 대입하지 않은 변수.
- **왜 문제**: `const`가 의도를 더 정확히 드러내고, 실수로 재할당하는 사고를 막는다.
- **고치는 법**: `let`을 `const`로 바꾼다.

### `no-const-assign` — `const`에 재할당

- **뜻**: `const`로 선언한 값에 다시 대입하려 함.
- **왜 문제**: 실행 중 `TypeError`가 난다.
- **고치는 법**: 재할당이 필요하면 `let`으로 바꾼다. 배열·객체의 내부 값 변경은 재할당이 아니므로 `const`를 유지해도 된다.

### `no-redeclare` — 같은 변수 두 번 선언

- **뜻**: 이미 선언된 이름을 같은 스코프에서 다시 `var`·`let`·`const`로 선언.
- **왜 문제**: 코드가 무엇을 가리키는지 흐려진다.
- **고치는 법**: 두 번째 선언에서 키워드를 지우고 재할당(`=`)으로 바꾸거나, 이름을 다르게 짓는다.

## 3. 비교·조건

### `eqeqeq` — 엄격 비교 사용

- **뜻**: `==` 또는 `!=`로 비교한 코드.
- **왜 문제**: 느슨한 비교는 형 변환을 하므로 `0 == ''`, `null == undefined`가 모두 참이 된다. 예측이 어렵다.
- **고치는 법**: `===`·`!==`로 바꾼다.

```js
// 나쁨
if (userInput == 0) { }

// 좋음
if (userInput === 0) { }
```

### `no-cond-assign` — 조건절 안에서 대입

- **뜻**: `if (a = 1)`처럼 조건절 안에서 `=`를 씀. 비교(`==`·`===`)와 오타로 뒤바뀐 경우가 많다.
- **왜 문제**: 대입은 항상 참이 되어 조건이 늘 성립한다.
- **고치는 법**: 비교이면 `===`로, 대입이 의도라면 대입만 밖으로 빼고 결과를 별도 변수에 담아 조건으로 쓴다.

### `no-constant-condition` — 상수 조건

- **뜻**: `if (true)`, `while (1)`처럼 값이 고정된 조건.
- **왜 문제**: 무한 루프이거나 죽은 분기다.
- **고치는 법**: `while (true)`가 의도한 무한 루프면 주석으로 이유를 남기거나 `for (;;)`를 쓴다. 그 외에는 조건을 실제 값으로 바꾼다.

## 4. 반복·비동기

### `for` 루프·`forEach` 대신 최신 배열 메서드

이 스킬은 `for` 루프를 오류로 잡지 않지만, 사용자 지침상 최신 배열 메서드를 권장한다. 결과에 `for` 문이 감지되면 보고서 마지막 "먼저 할 일" 항목에 다음 대체안을 한 줄로 안내한다.

- 새 배열이 필요하면 `map`
- 필터링이면 `filter`
- 합계·집계면 `reduce`
- 순회만 하면 `for...of`

### `no-await-in-loop` — 반복문 안 `await`

- **뜻**: `for` 반복문 안에서 매 반복마다 `await`을 씀.
- **왜 문제**: 요청이 하나씩 직렬로 나가서 느리다. 대개는 병렬 처리가 가능하다.
- **고치는 법**: `Promise.all(items.map(fn))`으로 바꾼다. 순서가 반드시 필요하다면 그대로 두되 이유를 주석으로 남긴다.

### `require-await` — `async`인데 `await` 없음

- **뜻**: `async` 함수 안에서 `await`이 한 번도 쓰이지 않았다.
- **왜 문제**: 굳이 `async`일 필요가 없다. 반환값이 자동으로 `Promise`로 감싸져 오해를 부른다.
- **고치는 법**: `async`를 지우거나, 실제로 `await`이 필요한 곳에서 사용한다.

### `no-callback` (사용자 관습)

콜백 스타일 API를 발견하면(예: `fs.readFile(path, (err, data) => {})`) 보고서에 대체안을 안내한다.

- Node.js는 `fs/promises` 사용
- 브라우저 API는 대개 이미 `Promise` 반환

## 5. 함수·객체

### `no-dupe-keys` — 객체 리터럴 키 중복

- **뜻**: 같은 객체 안에 같은 이름의 키가 두 번 이상 있음.
- **왜 문제**: 뒤에 쓴 값이 앞을 덮어 데이터가 소리 없이 사라진다.
- **고치는 법**: 오타이면 이름을 고치고, 병합이 의도이면 스프레드(`...`)로 명시한다.

### `no-dupe-args` — 매개변수 이름 중복

- **뜻**: 함수 선언에서 같은 이름의 매개변수를 두 번 씀.
- **왜 문제**: 스트릭트 모드에서는 문법 오류다.
- **고치는 법**: 이름을 다르게 준다.

### `no-func-assign` — 함수 선언에 재할당

- **뜻**: `function foo() {}` 다음에 `foo = 1`처럼 함수 이름에 값을 대입.
- **왜 문제**: 원래 함수를 잃는다. 실수인 경우가 대부분.
- **고치는 법**: 다른 이름의 변수를 쓴다.

### `getter-return` — 게터에 반환값 없음

- **뜻**: `get name() {}`인데 `return`이 없다.
- **왜 문제**: 게터는 값을 돌려주는 것이 목적이다. 없으면 `undefined`만 나온다.
- **고치는 법**: `return`을 추가한다.

## 6. 안전·품질

### `no-unreachable` — 도달 불가 코드

- **뜻**: `return`·`throw`·`break` 뒤에 있는 코드.
- **왜 문제**: 절대 실행되지 않는다.
- **고치는 법**: 지운다.

### `no-empty` — 빈 블록

- **뜻**: `if () { }`·`catch (e) { }`처럼 안이 빈 블록.
- **왜 문제**: 의도가 무엇인지 알 수 없다. `catch`에서 오류를 삼키면 진단이 불가능해진다.
- **고치는 법**: 필요 없으면 블록 자체를 지운다. 무시가 의도라면 주석을 남긴다: `catch (_) { /* ignore */ }`.

### `no-debugger` — `debugger` 문

- **뜻**: 코드에 `debugger;`가 남아 있음.
- **왜 문제**: 배포된 코드에서 개발자 도구가 열려 있으면 실행이 멈춘다.
- **고치는 법**: 배포 전에 지운다.

### `no-console` — `console.log`

- **뜻**: 코드에 `console.log`가 남아 있음.
- **왜 문제**: 자체 오류는 아니지만 배포 코드에는 남기지 않는 편이 낫다. 필요한 로그는 별도 로거로 뺀다.
- **고치는 법**: 지우거나 로거로 대체한다. 학습용 코드에는 이 규칙을 끄고 검사해도 된다.

### `no-eval` — `eval` 사용

- **뜻**: `eval(...)` 호출.
- **왜 문제**: 임의 코드를 실행하므로 큰 보안 구멍이 된다.
- **고치는 법**: `eval`을 쓰지 않는 방법으로 다시 짠다. JSON 파싱이면 `JSON.parse`, 함수 이름으로 분기하면 객체 매핑을 쓴다.

### `no-implied-eval` — 문자열을 코드로 실행

- **뜻**: `setTimeout("code", 100)`처럼 문자열을 넘겨 실행.
- **왜 문제**: 내부적으로 `eval`과 같다.
- **고치는 법**: 함수를 넘긴다: `setTimeout(() => code(), 100)`.

---

## 7. 표에 없는 규칙을 만났을 때

1. 규칙 이름을 그대로 원문에 남긴다. 학습자가 검색할 수 있어야 한다.
2. ESLint 공식 문서의 규칙 페이지(예: `https://eslint.org/docs/latest/rules/no-unused-vars`)에서 뜻을 확인한 뒤 한 문장으로 옮긴다.
3. 확실하지 않으면 "확인되지 않음"으로 적고 추측을 사실처럼 쓰지 않는다.
